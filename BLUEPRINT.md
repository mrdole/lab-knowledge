# lab-knowledge blueprint

Schemas and rules for the knowledge repo. The validator
(`agent-platform/mcp/knowledge/knowledge_core.py validate`) enforces everything marked
**(checked)**.

## 1. Layout

```text
lab-knowledge/
├── README.md, AGENTS.md, BLUEPRINT.md
├── .gitlab-ci.yml          includes agent-platform ci/knowledge.gitlab-ci.yml
├── docs/
│   ├── _template.md        files/dirs starting with "_" are ignored
│   ├── <area>/<slug>.md    areas: network, tooling, bench, gitlab, gotchas, ...
├── inventory/
│   ├── benches.yaml
│   └── devices.yaml
├── models/
│   └── registry.yaml       model servers (locations) and what each model is good for
└── catalog/                generated by tools/skills_index.py - do not edit
    ├── skills.json
    └── SKILLS.md
```

## 2. Docs

File names are lowercase and hyphenated, ending in `.md` **(checked)**. Each doc starts
with YAML frontmatter:

```yaml
---
title: Reaching the LLM server from the lab subnet   # required
kind: gotcha            # required: gotcha | howto | reference | policy
applies_to: [all]       # required list: "all" or profile names (firmware, pipeline, bench, it-debug, meta)
status: draft           # required: draft | verified
owner: rf-test-team     # required: who keeps it true
last_verified: 2026-10-29   # required when status is verified; YYYY-MM-DD, not in the future
tags: [network, proxy]  # optional, used in search ranking and list_docs(tag=...)
---
```

All of the above are **(checked)**, plus: non-empty body, no secret-looking strings, and
`applies_to` values must be real profiles (when validated with `--profiles-from`).

**Kinds**
- `gotcha`: something that breaks in a non-obvious way. Write it as Symptom (exact
  error text) / Cause / Fix / How confirmed.
- `howto`: a procedure. Numbered steps and a verification step.
- `reference`: facts: addresses, versions, names, tables.
- `policy`: rules agents must follow (e.g. RF safety). Usually `applies_to` specific
  profiles.

**Trust and staleness**
- `verified` + `last_verified` within 180 days → agents treat it as fact.
- `draft`, or verified more than 180 days ago (`stale: true` in search results) → a hint
  agents must confirm. Validation warns on stale verified docs.
- Search ranks drafts slightly lower than verified docs.

**Visibility.** The knowledge server only returns docs whose `applies_to` contains `all`
or the calling profile. Use this to keep, for example, IT network detail away from
firmware agents.

## 3. Inventory

`inventory/benches.yaml`
```yaml
benches:
  - name: bench-a            # required; also the bench-lock name and resource_group suffix
    location: <lab/room>
    runner_tag: bench-a      # GitLab runner tag of the host wired to this bench
    board: board-a           # DUT device name
    owner: <team>
```

`inventory/devices.yaml`
```yaml
devices:
  - name: sa-01              # required, unique
    kind: spectrum_analyzer  # required; "dut" for boards
    model: <vendor model>
    bench: bench-a           # required; must exist in benches.yaml
    visa: TCPIP0::192.0.2.10::inst0::INSTR   # required unless kind is dut
    read_only: true          # default true; false only if writes are ever allowed
    write_allowlist: []      # exact SCPI headers allowed when writes are enabled, e.g. [FREQ, POW]
    termination: "\n"        # optional read/write termination
    timeout_ms: 5000         # optional
    applies_to: [bench, firmware]   # optional; default [bench, firmware]
    notes: <free text>
```
Checked: required keys, unique names, bench exists, `read_only` is boolean,
`write_allowlist` is a list of strings (warning if set on a read-only device).

Bench write policy, enforced by the bench MCP server: writes need the session flag
`AP_BENCH_ALLOW_WRITE=1`, `read_only: false`, and the command's header exactly in
`write_allowlist`. No `;`-chained commands. Keep RF on/off (`OUTP`) out of allowlists so a
human always does it.

## 4. Catalog

`catalog/skills.json` is produced by `agent-platform/tools/skills_index.py gitlab ...` on
a schedule. It lists every `SKILL.md` found under `skills/`, `.opencode/skills/`,
`.agents/skills/` and `.claude/skills/` in the group's projects: name, description,
project, path, web_url, problems. It also lists duplicate names and similar descriptions.
The CI job opens an MR from `bot/skills-catalog` when it changes. Review new and
duplicate skills there.

## 5. Model registry

`models/registry.yaml` answers "which models exist where, and which one should do this
task?" It's read by the knowledge server (`list_models`, `recommend_model`) and
`agent-platform/tools/models.py`.

```yaml
locations:
  - name: corp-llm            # required
    access: api               # api (agents can call it) | interactive (people only, e.g. Copilot)
    data_boundary: internal   # internal | external (code leaves the network)
    base_url_env: AP_LLM_BASE_URL   # api locations need base_url or base_url_env
    api_key_env: CORP_LLM_KEY
    provider_id: corp
models:
  - id: gpt-oss-120b          # required; the id the server's /models returns
    name: GPT OSS 120B        # required
    locations: [corp-llm]     # required; must exist above
    params: 117B MoE (~5B active)
    context: 128K
    modalities: [text]        # text | image | video | audio
    tool_calling: good        # required: good | fair | none | unknown
    good_for: [coding]        # required; vocabulary below
    avoid_for: []             # vocabulary below
    platform_role: builder    # planner | builder | small | reviewer | scout (matches AP_MODEL_*)
    confidence: prior         # required: prior (vendor/reputation) | measured (our evals)
    evidence: []              # eval ids; required when confidence is measured
    notes: <free text>
```
All required fields, the vocabulary, the enums and location references are **(checked)**.

**Task vocabulary:** planning, orchestration, coding, code-review, tool-calling,
repo-scouting, test-running, reasoning, summarization, docs-writing, classification,
routing, long-context, document-understanding, vision, screen-reading, audio, sql.
The list lives in `knowledge_core.TASK_TAGS`, together with the words that map a
free-text task onto each tag.

**Ranking.** +2 per matching `good_for` tag and −3 per `avoid_for` tag. When the model
would do agentic work, tool-calling ability adds or subtracts. The current
`platform_role` breaks ties, and `measured` beats `prior`. Interactive-only models are
listed separately (`interactive_only`) unless that location is requested, because agents
can't call them.

**Keeping it true.**
- `tools/models.py probe --location corp-llm` compares the server's `/models` with the
  registry: ids that are served but not registered, and registered but not served.
- After a bake-off, the meta profile changes `confidence` to `measured` and lists the
  eval ids in `evidence`. Role changes then go to `core/platform.env` in agent-platform.

## 6. Rebuilding from scratch

1. Create the layout above. Add `docs/_template.md`.
2. Write `inventory/benches.yaml`, then `inventory/devices.yaml`.
3. Seed docs: at least the LLM-server access gotcha, CA trust, the build container, the
   flash procedure, RF safety policy, and GitLab tokens/labels.
4. Generate the catalog: `skills_index.py local <platform> <repos...> -o catalog`.
5. Add `.gitlab-ci.yml` including `ci/knowledge.gitlab-ci.yml`. Add the schedule with
   `AP_SKILLS_INDEX=1`.
6. Validate.
